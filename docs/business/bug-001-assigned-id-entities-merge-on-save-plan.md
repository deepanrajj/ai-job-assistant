# Bug 001 - Assigned-Id Entities Merge On Save Plan

Status: Completed

## Purpose

Decide and record how `Job` and `Task` should tell Spring Data that a
freshly built instance has never been stored, so that saving a new
entity issues an `INSERT` alone instead of a `SELECT` followed by an
`INSERT`.

The defect is described in
`tasks/bugs/bug-001-assigned-id-entities-merge-on-save.md`. That file
lists three candidate approaches and requires the choice and its
reasoning to be recorded here before any code changes.

## Current State

- `Job` and `Task` are Kotlin classes with `@Id val id: UUID`. The id is
  assigned by the caller, not generated by the database, and it is never
  null.
- Neither entity declares `@Version` nor implements `Persistable`.
- `DefaultJobService.createJob` builds a `Job` with `UUID.randomUUID()`
  and calls `jobRepository.save(job)`.
- `DefaultJobService.updateJob` loads the existing row, builds a
  **second, brand new** `Job` instance carrying the same id, and saves
  that.
- `Task` has no service yet. Tasks 010 to 012 will add one, and it will
  copy whatever shape `jobs` establishes.
- The backend coverage gate requires 100 per cent line **and** branch
  coverage, so anything added here must be fully exercised by tests.
- Tests run against H2 in PostgreSQL mode with the real Flyway
  migrations.

### Why The Extra Select Happens

`SimpleJpaRepository.save` is:

```java
if (entityInformation.isNew(entity)) {
    entityManager.persist(entity);
    return entity;
}
return entityManager.merge(entity);
```

With no `@Version` and no `Persistable`, Spring Data uses
`JpaMetamodelEntityInformation.isNew`, which answers the question by
testing whether the `@Id` is null. Our ids are assigned before the save
and are never null, so `isNew` is always false and every save takes the
`merge` branch.

`merge` is defined as "copy the state of this detached instance onto the
managed one", so it must first fetch the managed one. For a row that
does not exist yet, that fetch is a wasted `SELECT`, and the `INSERT`
follows anyway.

`merge` also returns a *different object* - the managed copy - and
leaves the caller's instance detached. That is the second half of the
defect: `repository.save(entity); return entity` looks correct and
silently returns an object whose later changes are never written.

### Measured Before The Fix

The defect was reproduced on this branch before the plan was finalised,
with a throwaway test that saved one new `Job` and read Hibernate's
counters. It reported:

```text
statements=2  loads=0  inserts=1  sameInstance=false
```

and the SQL log showed the two statements in order:

```text
select j1_0.id, ... from jobs j1_0 where j1_0.id=?
insert into jobs (company, ...) values (?, ...)
```

Both halves of the ticket are therefore confirmed rather than inferred:
one wasted statement per insert, and `save` handing back an object that
is not the one it was given.

`loads=0` is the useful surprise. The wasted `SELECT` finds nothing, so
Hibernate loads no entity and `entityLoadCount` stays 0 whether the
defect is present or not. See the Tests section - it means the statement
count is the only counter that can prove anything here.

## Decisions

### Decision 1: use `Persistable`, lifted into a `@MappedSuperclass`

This is option 2 from the bug ticket.

An entity may implement `org.springframework.data.domain.Persistable`
and answer `isNew()` for itself. Spring Data then trusts that answer
instead of inspecting the id. The entity tracks its own state with a
`@Transient` flag that starts out meaning "new" and is cleared by the
JPA lifecycle callbacks `@PostPersist` (it has just been inserted) and
`@PostLoad` (it came out of the database, so it clearly exists).

The flag lives in one shared `@MappedSuperclass` rather than being
copied into each entity.

Reasoning:

- `docs/context.md` section 5 plans thirteen further entities - `Note`,
  `TimelineEvent`, `Contact`, `Reminder`, `ApplicationDocument`,
  `SavedSearch`, `ImportCandidate`, `ResumeProfile`, `AiOutput`,
  `AiUsageEntitlement`, `AiUsageEvent` and more. Every one of them has
  an assigned `id` and would carry the same defect. Fixing this once in
  a base class is the difference between one place to get right and
  fifteen.
- The bug ticket asks for `Job` and `Task` to use the same mechanism so
  a third entity has an obvious pattern to follow. Inheriting a base
  class makes the pattern impossible to forget; copying eight lines
  makes it easy to forget.
- It needs no schema change, so nothing about it is a database decision.

### Decision 2: reject `@Version`

This is option 3 from the bug ticket.

`@Version` would fix `isNew` as a side effect, because Spring Data
treats a null version as "new". It is rejected because:

- It requires a Flyway migration adding a `version` column to `jobs` and
  `tasks`. `docs/context.md` section 5 does not model a version column,
  and adding optimistic locking is a persistence-strategy decision that
  deserves its own task rather than arriving inside a defect fix.
- It fixes the wasted `SELECT` on insert but leaves the update path
  merging, so the "merge returns a different instance" half of the
  defect survives.
- It buys a real feature - concurrent-update detection - that nothing
  currently asks for. Adding a feature in order to fix a bug is the
  wrong shape.

Revisit `@Version` when concurrent edits become real, which realistically
means after authentication and multi-device use exist.

### Decision 3: reject the per-entity copy of the flag

This is option 1 from the bug ticket. It is the same mechanism as
decision 1 without the shared base class. Rejected purely on
duplication: identical eight-line blocks in two entities today and
fifteen tomorrow, each one an opportunity to omit `@PostLoad` and
quietly re-break the update path.

### Decision 4: `updateJob` must mutate the loaded entity

This is the consequence the bug ticket does not spell out, and it is the
largest part of the work.

Once `Job` implements `Persistable`, a freshly constructed instance
reports `isNew() == true` **even when its id already exists in the
database**, because the flag belongs to the object, not to the id.
`DefaultJobService.updateJob` does exactly that today: it loads the row
and then builds a second `Job` object carrying the same id. After the
change, saving that second object takes the `persist` branch, and
`persist` on an id the persistence context already holds throws
`EntityExistsException` - which Spring's exception translation surfaces
to repository callers as `org.springframework.dao.DuplicateKeyException`.

That is a feature, not a casualty. Before the fix, the same code
silently *overwrote* the stored row, because merge means "copy my values
onto whatever is there". Measured against the unfixed code, saving a
rebuilt `Job` carrying an existing id reported
`no error; rows=1; company=Impostor Corp` - the original row's values
gone, with nothing raised. `save` could not tell a create from an
update. After the fix it can.

So `updateJob` changes from "rebuild the entity" to "load it and change
its fields", which is how JPA is meant to be used:

```kotlin
val job = jobRepository.findById(id).orElseThrow { jobNotFound() }
job.company = command.company
// ...remaining editable fields...
job.updatedAt = now()
return job
```

No `save` call is needed. The instance is managed, so Hibernate's dirty
checking writes the `UPDATE` when the transaction commits. Keeping an
explicit `jobRepository.save(job)` would also work - merging an already
managed instance is close to a no-op and issues no extra `SELECT` - but
it re-introduces the merge this bug is about, so it is left out and the
reliance on dirty checking is commented in the code.

This has a real cost: the editable properties of `Job` become `var`,
where `backend/AGENTS.md` section 2 says to prefer `val`. That rule is
about ordinary Kotlin code. A JPA entity is a mutable, tracked
representation of a database row by design, and the alternative -
rebuilding the object on every edit - is what produced this defect.
`id`, `userId` and `createdAt` stay `val`, because nothing may change
them.

`Task` needs no equivalent change: it has no service yet. Task 010 will
inherit the pattern.

### Decision 5: `@JvmField` on the inherited id

`Persistable<UUID>` is a Java interface declaring `UUID getId()`.
Kotlin does not let a property implement a Java interface method.
Writing `@Id override val id: UUID` fails to compile with

```text
Class 'Job' is not abstract and does not implement abstract member
fun getId(): ID?
'id' overrides nothing.
```

and writing both `val id` and `override fun getId()` fails with a JVM
platform declaration clash, because the property already generates a
method with that exact signature.

This was verified against this project's compiler and Kotlin version
before writing this plan, not assumed.

The resolution is `@JvmField`, which exposes the id as a plain public
field and generates no getter, leaving `override fun getId()` free to
provide the interface method. Kotlin call sites keep writing `job.id`
unchanged; the compiler simply reads the field instead of calling a
getter.

Hibernate is unaffected: `@Id` sits on the field, so it already uses
field access rather than property access.

### Decision 6: enable Hibernate statistics for all tests

The regression test has to prove the *absence* of a statement, which the
eye cannot do reliably. Hibernate's `Statistics` counts statements, but
only when `hibernate.generate_statistics` is on.

The property goes in `backend/src/test/resources/application.properties`
so every test shares it. The alternative - `@SpringBootTest(properties =
[...])` on the one test class - gives that class a different property
set, and a different property set means Spring builds and caches a
second application context. One shared context is worth more than
avoiding a counter that costs nothing while nobody reads it.

## Proposed Change

### New file

```text
backend/src/main/kotlin/com/smartjobtracker/persistence/AssignedIdEntity.kt
```

`com.smartjobtracker.persistence` is a new package. `backend/AGENTS.md`
section 1 groups production code by domain, and this class belongs to no
domain: it is the persistence mechanism every domain shares.

Shape:

| Member | Kind | Purpose |
| --- | --- | --- |
| `id` | `@Id @JvmField val id: UUID`, constructor parameter | the assigned primary key, inherited by every entity |
| `persisted` | `@Transient private var`, defaults to `false` | whether this instance is known to exist in the database |
| `getId()` | `override fun`, returns `id` | satisfies `Persistable<UUID>` |
| `isNew()` | `override fun`, returns `!persisted` | what `SimpleJpaRepository.save` branches on |
| `markPersisted()` | `protected fun`, annotated `@PostPersist` and `@PostLoad` | clears the flag after an insert or a load |

The class is `abstract`, annotated `@MappedSuperclass`, and implements
`Persistable<UUID>`.

`@MappedSuperclass` means "these mappings are inherited by subclasses,
but this class is not itself a table". It adds no column and therefore
needs no migration.

### Changed files

| File | Change |
| --- | --- |
| `jobs/Job.kt` | extends `AssignedIdEntity(id)`, drops its own `@Id val id`, editable fields become `var` |
| `tasks/Task.kt` | extends `AssignedIdEntity(id)`, drops its own `@Id val id`, fields stay `val` |
| `jobs/JobService.kt` | `updateJob` mutates the loaded entity instead of rebuilding it |
| `src/test/resources/application.properties` | adds `spring.jpa.properties.hibernate.generate_statistics=true` |

`Task` keeps `val` fields for now. Nothing mutates a task yet, and task
010 can turn the fields it edits into `var` when it has a reason to.

## Tests

### New file

```text
backend/src/test/kotlin/com/smartjobtracker/persistence/AssignedIdEntityTest.kt
```

A `@SpringBootTest @Transactional` class reading Hibernate `Statistics`
through
`entityManagerFactory.unwrap(SessionFactory::class.java).statistics`.

Each case clears the counters, performs one operation, flushes, and
asserts on the counts.

| Case | Asserts |
| --- | --- |
| saving a new job inserts without loading | `prepareStatementCount == 1` and `entityInsertCount == 1` |
| saving a new job returns the same instance | `saved` is the same object that was passed in, via `isSameAs` |
| saving a new task inserts without loading | the same two counters, after seeding and flushing a job and then clearing the counters |
| a loaded entity is not new | `findById(...)` then `isNew()` is `false`, proving `@PostLoad` fires |
| a saved entity is no longer new | `isNew()` is `false` after the save, proving `@PostPersist` fires |
| the `Persistable` id is the entity id | `(job as Persistable<UUID>).id` equals `job.id` |
| rebuilding an entity with an existing id is rejected | saving a second instance carrying a stored id raises `DuplicateKeyException` instead of overwriting the row |

The last row was added during implementation rather than planned. It
pins the behaviour change described under decision 4: the same code that
used to overwrite a row silently now fails loudly.

The last case exists for a specific reason. `job.id` compiles to a
direct field read because of `@JvmField`, so nothing in the other cases
ever executes `getId()`, and the 100 per cent line gate would fail on an
uncovered method. Reading the id through the interface is also the
honest way to check that the contract Spring Data relies on is wired up.

Only the first three cases can be written before the fix. The last three
name `isNew()` and `Persistable`, which do not exist on `Job` yet, so
writing them early produces a compile error rather than a test failure -
and a compile error demonstrates nothing about the defect. They are
added in step 6, once the base class exists.

`prepareStatementCount == 1` is the assertion that actually pins the
defect: measured against the unfixed code it is 2.

`entityLoadCount` was in an earlier draft of this plan and has been
removed. Measurement showed it reports 0 both before and after the fix,
because the wasted `SELECT` finds no row and therefore loads no entity.
It would have looked like a meaningful assertion while proving nothing -
exactly the failure mode `tasks/bugs/README.md` warns about.

### Existing tests

All existing tests must pass unchanged. Two are worth watching
specifically:

- `JobServiceTest.updates editable fields and preserves identity and
  creation time` exercises the rewritten `updateJob`.
- `JobCrudIntegrationTest`'s update case exercises it over HTTP.

Neither should need editing. Both assert on the returned job's field
values, and those values do not change. If either needs an assertion
weakened or removed, the change is wrong - see `AGENTS.md` section 4.

## Implementation Order

The order matters here: steps 3 and 4 each end in a failure that
explains the design, so neither should be skipped.

1. Add this plan and link it from `docs/business/README.md`.
2. Add `spring.jpa.properties.hibernate.generate_statistics=true` to the
   test properties.
3. Write the three statement-count and instance-identity cases of
   `AssignedIdEntityTest` **before** touching production code, and run
   them. They must fail with 2 statements instead of 1, and the
   `isSameAs` case must fail. A regression test that passes before the
   fix proves nothing (`tasks/bugs/README.md`). The remaining cases wait
   for step 6 because they will not compile until the base class exists.
4. Add `AssignedIdEntity`, and make `Job` and `Task` extend it. Run the
   backend tests. Expect the `JobServiceTest` and `JobCrudIntegrationTest`
   update cases to fail with `EntityExistsException` - this is decision
   4 arriving on schedule, not a mistake.
5. Rewrite `DefaultJobService.updateJob` to mutate the loaded entity,
   turning the editable `Job` properties into `var`. Everything goes
   green.
6. Add the three lifecycle and `Persistable` cases now that they
   compile, and confirm the coverage gate is satisfied.
7. Run `npm run backend:verify`.
8. Mark the bug fixed in its ticket and in `tasks/bugs/README.md`, and
   mark this plan `Completed` with a verified-state section.

Two notes for future readers.

`entityLoadCount` looks like the obvious counter for this defect and is
useless for it - the wasted `SELECT` finds no row, so it reports 0
whether the bug is present or not. `prepareStatementCount` is the one
that discriminates.

The exception raised when a rebuilt entity is saved over an existing id
is `EntityExistsException` at the JPA level, but repository callers see
Spring's translation of it, `DuplicateKeyException`. Assert on the
translated type when the call goes through a repository.
